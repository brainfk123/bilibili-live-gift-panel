# 原子属性编辑设计

## 背景与目标

属性编辑器只冻结当前属性的礼物和定时器规则，其他属性仍应继续响应直播事件。现有保存流程在前端读取完整配置、修改目标属性后，再用整块 `attributes`、`rules`、`timerRules` 等字段执行 PATCH。即使保存前重新 GET，其他属性仍可能在 GET 与 PATCH 之间变化，并被旧数组覆盖。

本设计把属性编辑意图移动到后端，在 `configStore` 同一把锁内读取最新状态、合并目标属性及其引用并原子持久化。目标是消除其他属性的丢失更新，同时保留现有 `/api/config` 供其他配置功能兼容使用。

## 已确认的并发语义

- 仅当前编辑属性被冻结；其他属性、礼物收据、统计和贡献继续更新。
- 同一属性允许多个编辑页面同时持有租约。
- 同一属性被多个页面依次保存时，后提交者覆盖目标属性及其所属礼物/定时器规则。
- 后提交者不得覆盖其他属性、其他属性的规则、实时值或数组顺序。
- 已跳过的礼物或定时器规则不补放。

## 模块与接口

新增一个后端原子属性编辑模块。它的接口只表达两个用户意图：准备现有属性的编辑会话，以及提交一个属性编辑。稳定 ID 补齐、租约、引用迁移、合并、校验和持久化都隐藏在模块实现中。

### 准备编辑会话

`POST /api/attribute-edits/session`

请求使用以下两种目标之一：

```json
{ "attributeId": "attribute-..." }
```

或旧配置无 ID 时：

```json
{ "legacyName": "积分" }
```

约束：

- 两个字段必须且只能提供一个。
- `attributeId` 必须唯一命中一个现有属性。
- `legacyName` 必须唯一命中一个无 ID 的现有属性；后端在配置锁内生成并持久化稳定 ID。
- ID 持久化成功后创建 15 秒编辑租约。若租约 token 生成失败，已补齐的 ID 可以保留，因为它是安全且幂等的迁移。
- 响应返回稳定 ID、24 字符租约 token、到期时间和权威配置快照。
- 前端仅在成功响应后挂载编辑器。

### 提交属性编辑

`POST /api/attribute-edits`

现有属性请求：

```json
{
  "target": {
    "kind": "existing",
    "attributeId": "attribute-...",
    "leaseToken": "AAAAAAAAAAAAAAAAAAAAAAAA"
  },
  "attribute": {},
  "giftRules": [],
  "timerRules": [],
  "giftCatalogUpserts": []
}
```

新建属性请求：

```json
{
  "target": { "kind": "new" },
  "attribute": {},
  "giftRules": [],
  "timerRules": [],
  "giftCatalogUpserts": []
}
```

约束：

- 现有属性按稳定 ID 定位，并验证 `leaseToken` 仍属于该属性。租约不是排他写锁，因此多个有效 token 均可提交。
- 新建属性不需要租约，稳定 ID 由后端生成。
- 客户端不得覆盖稳定 ID、模板来源等服务端管理字段。现有属性保留这些字段，新属性由服务端初始化。
- 最终名称必须非空、非保留名且唯一。
- 成功响应返回目标稳定 ID、最终名称、是否新建以及完整权威配置快照。前端以该快照替换本地缓存，然后关闭编辑器并释放租约。
- 失败时编辑器和租约保持有效，本地配置不得提前提交草稿。

## 后端原子合并

原子提交必须在 `configStore` 锁内完成以下顺序：

1. 检查配置是否允许修改并读取最新已提交状态。
2. 克隆最新状态。
3. 对现有属性按稳定 ID 唯一定位，对新属性生成唯一稳定 ID。
4. 记录现有属性当前存储名称。后提交者不使用打开页面时的旧名称作为冲突条件，因此满足最后写入获胜。
5. 在原属性位置替换目标；新属性追加到属性数组末尾。
6. 合并目标所属礼物和定时器规则：
   - 现有目标规则按 ID 替换并保持原组位置；
   - 请求中省略的目标规则删除；
   - 新规则确定性插入目标规则组末尾；
   - 其他属性的规则和相对顺序保持不变。
7. 礼物目录按礼物 ID 就地更新或追加，不覆盖未提交的目录项。
8. 若目标改名，使用后端公式 tokenizer 只重写标识符，并原子更新：
   - 礼物规则和定时器规则的 `attributeName`、公式和条件；
   - 展示场景的属性名称；
   - 活动的属性列表、初始值、结果值、获胜属性和里程碑；
   - 公式预设的来源属性和公式标识符。
9. 不修改历史日志、礼物收据、贡献和统计中的历史名称。
10. 对完整候选状态执行规范化、配置校验和公式校验。
11. 通过既有多分片事务原子持久化；成功后再发布缓存和通知监听器。

后台礼物或定时器更新与该提交共享 `configStore` 锁，因此它们只可能完整发生在属性编辑提交之前或之后，不会出现客户端 GET 与整块 PATCH 之间的丢失更新窗口。

## 前端变化

- 新增独立传输适配器，严格解析会话准备和属性提交响应。
- 现有属性打开流程改为调用会话准备接口；不再通过完整配置 PATCH 为旧属性补 ID。
- 编辑器仍保留本地草稿、模拟、时间格式和租约健康提示。
- 保存时仅发送目标属性、目标所属规则和必要礼物目录增量，不再构造或 PATCH 完整配置字段。
- 删除该编辑路径中的前端跨数组名称迁移和保存前整配置 GET；后端返回的权威状态成为唯一提交结果。
- 现有 `/api/config` 与其他配置编辑器保持不变。

## 错误合同

- `400`：请求结构、字段、属性草稿、规则、公式或完整候选配置非法。
- `403`：跨站请求。
- `404`：稳定 ID 或旧名称未唯一命中现有属性。
- `409 lease_lost`：现有属性租约已失效。
- `409 name_conflict`：最终名称与其他属性冲突。
- `409 mutations_blocked`：配置恢复、重置或不支持版本使写入被阻止。
- `500`：持久化失败；响应不包含内部路径或原始错误。
- 未知方法返回 `405` 和准确 `Allow`；所有响应设置 `Cache-Control: no-store`。
- 请求体限长、严格 JSON、拒绝未知字段和尾随 JSON，并复用现有同源校验。

同一属性被其他页面先保存不产生版本冲突。只要稳定 ID 仍存在、租约有效且最终名称合法，后提交者覆盖目标定义和目标所属规则。

## 验证合同

### 后端单元与 HTTP

- 旧属性无 ID 时安全补 ID并创建租约；重复/歧义名称拒绝。
- 现有属性保持稳定 ID和数组位置；新属性生成 ID并追加。
- 同一属性两个有效租约依次提交，第二次结果最终获胜。
- 名称迁移覆盖全部当前引用，只替换公式标识符，不修改历史记录或名称子串。
- 目标规则增删改保持其他规则顺序。
- 非法租约、目标消失、名称冲突、未知/尾随/超大 JSON、跨站请求正确拒绝。
- 写盘故障和事务恢复保证全有或全无。

### 确定性并发测试

- 客户端打开属性 A 后，通过真实礼物路径把未冻结属性 B 更新，再提交 A；B 的值、收据、统计和数组顺序必须保留。
- 用定时器路径重复同一交错。
- 在原子提交持锁期间触发 B 更新，验证 B 的更新完整发生在提交之后且不丢失。
- 新建属性提交前更新/重排现有属性，提交后保留最新状态并只追加新属性。

### 前端与发布门禁

- 会话准备成功前不挂载编辑器；失败保留引导。
- 保存请求只包含目标聚合，不包含其他属性完整数组。
- 保存失败保持草稿和租约；成功使用权威响应并恰好释放一次。
- 全量前端、类型检查、Go、Go race、UI、EXE 和嵌入资源清单全部通过。

## 范围外

- 不把通用 JSON Patch 或任意操作列表暴露给客户端。
- 不迁移其他配置编辑器到新接口。
- 不改变旧 `/api/config` 的兼容语义。
- 不引入数据库、消息队列、事件补放或发布版本变更。
