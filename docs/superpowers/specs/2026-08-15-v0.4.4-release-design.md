# v0.4.4 Release Design

## Goal

Publish the current committed `master` as `v0.4.4` without including any existing uncommitted files from the main working tree.

## Release contents

The release presents the completed user-facing work as one patch release:

- atomic attribute editing and crash-safe local recovery;
- gift-user identity variables and random formula selection;
- day/hour/minute/second attribute-time editing with validated shortcuts;
- per-attribute rule freezing while that attribute is being edited;
- gift-clip export quality, hidden FFmpeg processes, and packaged UI reliability.

The bundled changelog uses the title `属性编辑与规则体验升级` and a concise Chinese summary covering these capabilities.

## Versioned files

The release preparation commit changes only:

- `package.json`;
- `package-lock.json`;
- `gift-panel-changelog.json`;
- changelog/version tests that encode the bundled release contract.

Both package manifests move from `0.4.3` to `0.4.4`. The bundled changelog contains exactly the `0.4.4` fallback release dated `2026-08-15`.

## Verification

Before external publication, run the release-relevant gates on the exact release commit:

1. changelog and version-focused tests;
2. TypeScript typecheck and full frontend tests;
3. full Go tests and full race tests;
4. UI and Windows executable builds;
5. embedded UI manifest/handler closure tests;
6. release-workflow contract tests and `git diff --check`.

The pre-existing uncommitted files in the main working tree must remain unstaged and unmodified by the release commit.

## Publication flow

1. Commit the version/changelog update on `master`.
2. Push `master` to `origin` without force.
3. Create an annotated `v0.4.4` tag at the verified release commit.
4. Push only that tag.
5. Monitor the tag-triggered GitHub Actions release workflow to completion.
6. Verify the published GitHub Release, signed Windows asset, checksum, update manifest, changelog asset, and release tag association.

No local unsigned development executable is uploaded manually. Signing and publication remain owned by the release workflow and its protected environment.

## Failure handling

- If any local gate fails, do not push or tag.
- If the `master` push is rejected, stop and inspect remote divergence; never force-push.
- If the workflow fails before publication, diagnose the failed job and rerun only after the release contract remains intact.
- If a partial GitHub Release exists, use the workflow's documented repair path for the same immutable tag rather than moving or recreating the tag.
