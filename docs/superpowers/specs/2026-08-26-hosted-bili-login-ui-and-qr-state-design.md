# Hosted B 站登录 UI 与二维码状态设计

日期：2026-08-26

## 1. 目标

重构 Hosted 普通用户的 B 站登录页，使其与管理员系统使用同一套浅色视觉语言，并让二维码创建、等待扫码、已扫码待确认、网络重试、过期和验证成功都有清晰且可访问的反馈。

同时修正当前二维码轮询合同的两个问题：

- B 站返回的“未扫码”和“已扫码待确认”被合并成同一个内部错误，前端无法展示真实阶段；
- 前端每 2 秒轮询一次，但生产端单二维码每分钟只允许 12 次、单 IP 每分钟只允许 20 次，正常等待会被限流并错误显示成“网络暂不可用”。

本设计覆盖普通登录、迁移确认和管理员更换 B 站服务账号三个二维码流程。它不改变主播账号与目标直播间相互独立的产品边界。

## 2. 非目标

- 不保存普通用户的 B 站 Cookie、刷新令牌或二维码密钥。
- 不让登录用 B 站 UID 代表目标直播间所有权。
- 不改变邀请码兑换、管理员邮箱登录或高风险操作授权。
- 不扩大生产限流额度；通过客户端调度与现有限额对齐。
- 不在本规格内部署生产环境。完成后先本地验收，提交和部署分别取得确认。

## 3. 二维码状态合同

### 3.1 适配器内部阶段

`biliqr.Adapter` 把 B 站轮询结果规范化为正常阶段，而不是把所有非终态都建模为错误：

| B 站数据码 | 内部阶段 | 语义 |
| --- | --- | --- |
| `86101` | `waiting` | 尚未扫码 |
| `86090` | `scanned` | 已扫码，等待手机确认 |
| `0` | `verified` | 已确认，可继续完成身份验证 |
| `86038` | 终态错误 `expired` | 二维码已过期 |

验证器返回一个带阶段的内部结果。`waiting` 和 `scanned` 不包含 UID 或完成时间；只有 `verified` 可以携带现有的 `Verification`，并继续接受 UID 与完成时间校验。上游超时、取消、未知状态和无效响应仍走现有错误边界。

### 3.2 身份服务与 HTTP 响应

身份服务公开以下轮询状态：

- `pending`：等待扫码；
- `scanned`：已扫码，等待手机确认；
- `verified`：已有主播账号验证成功；
- `registration_required`：新身份需要兑换邀请码；
- `expired`：二维码过期。

`pending` 和 `scanned` 都返回原挑战的 `expiresAt`，并保留挑战供后续轮询。公开响应不得包含 UID、Cookie、二维码密钥、内部账号 ID 或 B 站原始响应。已有 `pending` 客户端合同保持兼容；`scanned` 是唯一新增状态。

### 3.3 所有二维码消费者

三个流程必须统一识别 `scanned`：

- 普通登录自动继续轮询并显示“已扫码，请在手机确认”；
- 迁移确认保留当前验证挑战，不把 `scanned` 当作拒绝或过期；
- 管理员更换服务账号保留当前挑战并显示同样的确认提示。

各流程继续拥有自己的业务动作和权限边界，不共享挑战或凭据。

## 4. 普通登录页

### 4.1 布局

登录页采用与管理员系统一致的浅灰蓝背景和白色主卡片。主卡最大宽度约 860px，桌面端为双栏：

- 左栏：标题、两步说明、当前状态、到期时间和错误恢复信息；
- 右栏：约 280px 的二维码和操作区。

手机端改为单列，二维码居中且不超过 `72vw`。所有按钮使用紧凑尺寸、居中文字、对称 padding，并尽量在操作区右对齐。页面不得产生横向滚动。

### 4.2 可见状态

| 状态 | 页面表现 |
| --- | --- |
| 创建中 | 二维码骨架、小型 spinner、“正在创建二维码” |
| 等待扫码 | 蓝色中性提示、“请使用 B 站客户端扫码” |
| 已扫码 | 绿色提示、“已扫码，请在手机确认”，二维码继续保留 |
| 网络失败 | 琥珀色提示、下一次重试时间、“立即重试” |
| 请求受限 | 琥珀色提示、“请求较频繁，稍后自动重试”，不冒充普通断网 |
| 已过期 | 移除二维码，主操作改为“重新生成” |
| 验证成功 | 成功反馈后进入主播工作区或邀请码兑换页 |
| 不可恢复错误 | 停止自动轮询，允许返回或重新生成，不反复请求 |

状态文本使用 `role="status"` 和合适的 `aria-live`。焦点、busy、disabled、hover 和按下反馈必须完整；`prefers-reduced-motion` 下关闭非必要动画但保留静态状态差异。

### 4.3 手机同机确认

如果服务器返回经过现有白名单验证的 `verificationUrl`，窄屏页面显示“在本机打开 B 站确认”。桌面端隐藏该入口并保留扫码。链接只能使用已经由服务端和客户端共同校验的 B 站官方 HTTPS 路径，不接受任意 URL。

### 4.4 二维码过期与重新生成

二维码过期后不自动换码，避免用户正在手机端处理旧二维码时页面静默切换：

- 立即停止旧挑战轮询，并移除失效二维码及对应的手机跳转链接；
- 原二维码区域保留固定占位，显示“二维码已过期”，避免卡片高度和操作位置跳动；
- 主操作变为“重新生成”，取消仍返回登录入口；
- 点击重新生成后进入创建中状态，按钮保持原宽度、禁用重复提交并显示 spinner；
- 新挑战创建成功后，在原位置替换二维码、到期时间和手机跳转链接，并从 `waiting` 重新开始轮询；
- 创建失败时保留错误提示与“再次尝试”，不自动循环创建新挑战。

旧挑战在进入过期状态时已经由服务端终结；重新生成必须创建全新的挑战，不复用旧挑战 ID、二维码或验证链接。

## 5. 轮询与重试

普通登录使用单一 `setTimeout` 调度器，不使用永久 `setInterval`，并保证同一挑战最多一个请求在途。

- 健康的 `pending` 或 `scanned` 响应后，6 秒再轮询；
- 网络错误或 `temporarily_unavailable` 后，按 2、4、8、15 秒退避，之后保持 15 秒；
- `rate_limited` 显示独立提示并至少等待 15 秒；
- 任意成功轮询清空连续失败次数；
- “立即重试”仅在没有请求在途且距离上次尝试至少 2 秒时启用；
- 过期、取消、验证成功、不可恢复错误或页面卸载都会取消计时器；
- 页面卸载继续遵守现有挑战清理和迟到会话补偿语义。

重试倒计时只显示剩余秒数，不暴露挑战 ID。自动与手动重试共用同一调度器，避免竞态和重复请求。

## 6. 模块边界

预计变更集中在以下边界：

- `goserver/internal/hosted/identity/biliqr`：B 站数据码到内部阶段的规范化；
- `goserver/internal/hosted/identity`：带阶段的验证器合同、身份服务和 HTTP 状态；
- `src/hosted/api.ts`：严格解析新增 `scanned` 响应；
- `src/hosted/auth.ts`：普通登录状态控制、单计时器调度和手动重试；
- 迁移与管理员服务账号控制器：保留并展示 `scanned` 挑战；
- `src/hosted/shell.css`：登录页布局、状态、按钮、响应式与减少动画样式。

二维码状态文案和视觉 token 可以共享，但三个业务控制器保持独立。不得为了复用把迁移、管理员权限或普通登录会话混入一个大型控制器。

## 7. 错误处理与隐私

- `rate_limited`、`temporarily_unavailable`、浏览器网络异常和无效响应必须可区分；
- 网络错误保留尚未过期的二维码，终态错误立即清除二维码来源；
- 日志只允许记录内部请求关联、错误类别、HTTP 状态和耗时，不记录挑战 ID、二维码 URL、Cookie、UID 或邀请码；
- 前端错误对象和 DOM 不得保留服务器响应中的未知字段；
- 取消和过期继续触发适配器的内存清理，二维码状态不写入 MySQL、COS 或浏览器持久存储。

## 8. 验证策略

### 8.1 Go

- 先用失败测试覆盖 `86101 → waiting`、`86090 → scanned`、`0 → verified` 和 `86038 → expired`；
- 验证 `scanned` 不销毁挑战，下一次轮询仍可成功；
- 验证身份服务与 HTTP 返回精确的 `scanned` 结构；
- 验证任何公开响应和日志均不携带 UID、Cookie、二维码密钥或原始 B 站响应；
- 回归普通登录、迁移证明和服务账号凭据消费路径。

### 8.2 TypeScript

- 严格接受 `scanned + expiresAt`，拒绝缺字段和附加身份字段；
- 验证 6 秒健康轮询、2/4/8/15 秒退避、限流等待、手动重试冷却和单请求在途；
- 验证取消、过期、成功、卸载及迟到会话补偿；
- 验证迁移和管理员服务账号不会把 `scanned` 当作失败。

### 8.3 浏览器与布局

使用本地可控状态覆盖创建中、等待扫码、已扫码、网络失败、请求受限、过期、成功和不可恢复错误。在桌面宽度和 iPhone 窄屏逐状态检查：

- 无横向裁切；
- 双栏与单列切换正确；
- 二维码尺寸、按钮对齐和 padding 对称；
- 手机跳转入口只在窄屏显示；
- 键盘焦点、加载动画和减少动画偏好正确。

### 8.4 生产前回归

使用当前已建立的生产复现步骤：生成临时二维码但不扫码，持续等待至少一分钟。验收要求页面始终保持正常等待状态，不再因自身轮询节奏进入“网络暂不可用”，访问日志中也不得出现由正常单挑战等待造成的 429。

任何生产验证都不得解析、记录或分享二维码内容。生产部署需要单独确认。

## 9. 验收标准

1. 普通登录页在桌面和手机均紧凑、对齐且无裁切。
2. 三个二维码流程都能区分未扫码与已扫码待确认。
3. 正常等待一分钟不会触发自身限流。
4. 网络不稳定时保留有效二维码，并按约定退避或允许受控手动重试。
5. 手机可以通过白名单 B 站链接在本机完成确认，桌面不显示该入口。
6. 取消、过期和卸载后没有遗留计时器、挑战或迟到登录会话。
7. UID、Cookie、二维码密钥、邀请码和会话材料不进入 DOM、错误文本或普通日志。
8. 本地自动测试、类型检查、Hosted 构建和逐状态浏览器验收全部通过后，才进入提交与部署确认。
9. 二维码过期后不会自动换码；手动重新生成期间不能重复提交，失败后可以安全再次尝试。
