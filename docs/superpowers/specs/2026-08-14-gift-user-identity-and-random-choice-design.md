# 礼物用户身份条件与随机多选一公式设计

**状态：** 已确认设计，待实施计划
**日期：** 2026-08-14
**基线：** `d8f288314172`

## 1. 目标与范围

本次需求完成三项工作：

1. 把每条送礼事件中已经存在的用户身份注入礼物公式环境，作为可引用的只读变量和命名枚举。
2. 给礼物规则增加独立触发条件，并在小白模式提供不需要手写公式的身份条件编辑器。
3. 给 Go 公式求值器增加任意参数数量、均匀随机且惰性求值的 `RANDOMCHOICE(...)` 函数。

本轮明确不包含：

- 改变 B 站身份解析协议、粉丝牌识别来源或大航海特殊礼物的目录定义。
- 增加字符串类型、字符串比较或通用枚举类型；公式引擎继续只计算数值。
- 改变 `RAND()`、`RANDBETWEEN()`、`IF()` 或现有礼物计算公式的语义。
- 为定时规则增加用户身份；定时事件没有送礼用户上下文。
- 改变随机数分布、引入可配置权重或无放回抽样。

## 2. 方案与架构边界

采用“独立条件字段 + 数值枚举常量”的方案。

不把条件编码为 `IF(条件, 新值, 原值)`，因为这种写法无法区分“规则没有触发”和“规则触发后值不变”，还会污染每日触发次数、规则命中日志与后续统计。

不增加 `是舰长`、`是提督` 等多组布尔变量，因为范围判断会变成多项组合；单一有序身份变量可以直接表达“舰长及以上”。

公式上下文由 Go 服务端统一构造。真实礼物执行和配置页公式预览必须调用同一个身份映射与环境构造 seam，不能在前端复制身份数值或在两个后端入口分别维护常量。

## 3. 用户身份变量与枚举

### 3.1 公式名称

礼物公式环境新增以下只读系统名称：

| 名称 | 数值 | 含义 |
|---|---:|---|
| `用户身份` | 运行时决定 | 当前送礼用户的身份等级 |
| `普通用户` | 0 | 没有粉丝团或大航海身份 |
| `粉丝团` | 1 | 粉丝团成员，但不是大航海 |
| `舰长` | 2 | 舰长 |
| `提督` | 3 | 提督 |
| `总督` | 4 | 总督 |

典型公式：

```text
用户身份>=舰长
用户身份=粉丝团
IF(用户身份>=提督, 积分+100, 积分+10)
```

公式语言继续使用现有数值相等运算符 `=`；UI 生成的条件必须使用求值器已经支持的运算符，不能引入只在前端成立的新语法。

### 3.2 运行时映射

现有礼物事件/礼物回执的 membership 语义映射为：

- 空值或未知值 → `普通用户`
- `fan` → `粉丝团`
- `captain` → `舰长`
- `admiral` → `提督`
- `governor` → `总督`

映射使用产品语义等级，不暴露 B 站原始 `guard_level` 的 3/2/1 编码。用户身份取自该条礼物事件，不根据礼物名称、价格或特殊礼物 ID 猜测。

### 3.3 保留名称

`用户身份`、`普通用户`、`粉丝团`、`舰长`、`提督`、`总督` 是公式保留名称：

- 系统值拥有固定含义，属性不得覆盖。
- 配置编辑器禁止新建或重命名为这些名称，并显示稳定中文错误。
- 服务端保存校验是最终防线，不能只依赖前端禁用。
- 公式预设、变量收集和属性重命名不得把这些系统名称当成可重命名的用户属性。

如果载入历史配置时已经存在同名属性，不做静默重写或自动改名；保存时返回明确冲突错误，由用户选择新属性名，避免悄悄改变公式含义。

## 4. 礼物规则触发条件

### 4.1 数据模型

Go `giftRule` 和 TypeScript `GiftRule` 增加可选字段：

```json
{
  "condition": "用户身份>=舰长"
}
```

空字符串或省略字段表示无条件触发，保证旧配置行为不变。

### 4.2 执行顺序

每次礼物数量展开、每条匹配规则的处理顺序为：

1. 检查规则启用状态、礼物 ID、最低价格和每日上限等现有门槛。
2. 用当前属性值、`price`、`用户身份` 和五个身份枚举常量构造公式环境。
3. 条件为空则视为真；否则计算 `condition`。
4. 条件结果为有限非零数时计算并应用 `formula`。
5. 条件为零、非有限数或求值失败时，本次规则不执行。

未通过条件的规则：

- 不修改属性；
- 不增加每日触发次数；
- 不写入成功的规则命中或属性变化日志；
- 不阻断同一礼物的其他规则和后续礼物处理。

条件按每个礼物数量和每条规则重新计算，因此条件可以引用会被前一次应用改变的当前属性值。身份和价格在同一条礼物事件内保持不变。

### 4.3 校验与预览

配置保存时，礼物规则的 `condition` 与 `formula` 都在礼物上下文中校验。条件可以引用属性、`price` 和身份系统名称；定时规则仍不能引用礼物专属变量。

公式预览请求增加模拟用户身份，使用整数 0–4 的严格枚举。缺省值为 `普通用户`，非法值返回 HTTP 400 与稳定中文消息。预览响应必须区分：

- 条件未命中：显示“本次不会触发”，属性保持原值；
- 条件命中：显示原值和公式结果；
- 条件或公式无效：显示既有公式错误，不伪装成未命中。

## 5. 小白模式与高级模式

### 5.1 小白条件编辑器

现有“小白模式：用一句话配置”增加两个联动下拉框：

```text
触发条件：[不限 / 身份等于 / 身份至少] [粉丝团 / 舰长 / 提督 / 总督]
```

序列化规则：

| 选择 | 保存的 condition |
|---|---|
| 不限 | 空字符串 |
| 身份等于 + 粉丝团 | `用户身份=粉丝团` |
| 身份至少 + 舰长 | `用户身份>=舰长` |

“身份至少”利用 0–4 的单调等级，因此 `用户身份>=舰长` 同时匹配舰长、提督和总督，但不匹配粉丝团。

### 5.2 高级条件

“高级规则”区域增加独立的“触发条件（可留空）”公式输入框，与“触发后属性值”分开。高级输入可以使用任意合法数值条件，不限于身份。

小白模式只反向识别以下标准形式：

- 空条件；
- `用户身份=<身份常量>`；
- `用户身份>=<身份常量>`。

若高级条件不是标准形式，小白条件选择器显示“高级条件”，并保持原表达式不变。用户只有主动选择新的小白条件时才覆盖高级表达式。

### 5.3 模拟身份

规则模拟区增加“模拟用户身份”选择，选项为普通用户、粉丝团、舰长、提督、总督，默认普通用户。该选择只影响预览请求，不写入礼物规则，也不改变直播中的真实身份。

当小白条件为“身份等于”或“身份至少”时，不自动篡改模拟身份；用户可以分别验证命中和不命中两种结果。

## 6. `RANDOMCHOICE(...)` 函数

### 6.1 语法与返回值

新增公式函数：

```text
RANDOMCHOICE(表达式1, 表达式2, ...)
```

- 参数数量必须至少为 1，没有固定上限，实际长度受现有公式文本和解析资源限制。
- 一个参数时直接计算并返回该参数，不调用随机数生成器。
- 两个及以上参数时，在 `[0, 参数数量)` 中均匀选择一个索引并返回对应表达式的结果。
- 返回值仍为 `float64`，不引入字符串或复合类型。

### 6.2 惰性求值

`RANDOMCHOICE` 只求值被选中的参数，未选参数不得执行。例如随机选择第一项时：

```text
RANDOMCHOICE(10, 1/0)
```

返回 10，未选中的除零不应使整条公式失败。被选中的参数本身求值失败时，按现有公式错误语义失败。

实现必须在函数节点内部先选择索引再调用对应参数节点，不能沿用普通函数“先计算所有参数”的路径。

### 6.3 随机性与事务一致性

`RANDOMCHOICE` 复用现有 `formulaRandomIntn` 注入 seam，与 `RANDBETWEEN` 使用同一随机来源：

- 单次求值只抽取一次索引；
- 测试可注入确定性索引；
- 礼物事务提交后恢复时沿用已持久化结果，不重新求值或重新抽取；
- 不单独创建新的全局随机数实例。

## 7. 前后端接口与深模块边界

身份知识收敛在 Go 公式上下文模块：

- membership → 数值等级的映射只有一份；
- 系统常量注入只有一份；
- 真实执行、配置校验和公式预览都通过该模块；
- UI 只持有用于展示和提交预览枚举的稳定 0–4 值，不重新解释 B 站 membership 字符串。

礼物条件属于 `GiftRule`，不创建第二套“身份规则”存储。小白模式只是该字段的受限编辑器，高级模式编辑同一个字段。

随机函数属于现有公式求值器的函数调用 seam，不增加前端随机逻辑。预览和直播执行都由 Go 求值，避免浏览器和服务端结果分叉。

## 8. 错误处理与兼容性

- 旧规则缺少 `condition` 时行为完全不变。
- 未知 membership 降级为普通用户，不因上游新增身份字符串中断礼物处理。
- 零参数 `RANDOMCHOICE()` 返回稳定的参数数量错误。
- 非法条件在配置保存/预览时显式报错；如果历史或损坏状态绕过校验进入运行时，则安全跳过该规则，不中断 durable inbox 消费。
- 保留名称冲突由配置校验拒绝，不静默覆盖系统值。
- 导入、导出、配置备份和模板复制必须保留 `condition` 字段。

## 9. 测试策略

### 9.1 Go 公式测试

- 五个身份常量与 `用户身份` 的数值。
- `RANDOMCHOICE` 的 0、1、2 和多参数行为。
- 注入首项、中间项和末项索引，证明等概率索引范围和只抽取一次。
- 未选错误分支不求值，被选错误分支返回错误。
- 嵌套 `IF`、`RANDOMCHOICE`、`RANDBETWEEN` 和属性表达式。
- 礼物事务恢复不会重新调用随机 seam。

### 9.2 Go 规则与配置测试

- membership 的五级映射和未知值降级。
- 条件命中/不命中、等于/至少、价格与属性联合条件。
- 多数量礼物逐次重算条件。
- 未命中不增加触发次数、不写成功日志。
- 规则条件无效时安全跳过，后续规则继续。
- 保存校验接受礼物身份变量、拒绝定时规则引用礼物变量。
- 六个保留名称的属性冲突。
- 预览的普通用户默认值、五种合法身份、非法身份、命中和跳过响应。

### 9.3 TypeScript/UI 测试

- `GiftRule.condition` wire round-trip。
- 小白编辑器生成空、等于和至少条件。
- 标准高级条件反向识别；非标准高级条件保持不变。
- 模拟身份传入后端且不写入规则。
- 条件未命中、命中、错误三种预览状态。
- 保存、重新打开、属性重命名和公式预设不会错误改写身份保留名称。

## 10. 提交与回滚边界

实施计划应拆为可独立审查的提交：

1. 公式身份常量、统一环境构造与 `RANDOMCHOICE`。
2. 礼物规则 `condition` 的后端模型、校验、预览和运行时语义。
3. TypeScript 类型/adapter 与小白模式、高级条件、模拟身份 UI。
4. 全量集成测试、文档与兼容性收尾。

前两步保持 UI 旧行为可用；第三步只编辑已有 `GiftRule.condition`，不创建并行存储。任一步出现问题都可以按提交边界回滚，不得把身份解析协议、定时规则或加权随机混入本轮。

## 11. 完成标准

- 任意礼物规则公式和条件都能引用 `用户身份` 及五个命名身份常量。
- 小白模式无需手写公式即可配置身份等于或身份至少条件。
- 高级条件与小白条件编辑同一字段且不会互相静默覆盖。
- 预览和真实礼物处理使用相同身份环境。
- `RANDOMCHOICE` 支持任意正参数数量、均匀选择和惰性求值。
- 旧配置与无条件礼物规则行为不变。
- 所有聚焦、全量、race、类型检查和构建门禁通过。
