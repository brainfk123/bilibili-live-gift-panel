# 公式结果赋值语义设计规格

**日期**：2026-08-01

## 1. 目标

将礼物规则中的公式结果从“变化量”改为“目标属性的新值”。公式计算结果直接写入目标属性，主播可以用属性自身作为变量表达递增、翻倍和条件赋值。

本次修改是全局语义变更，用户已明确选择不保留旧的“增加/赋值”兼容选项。已有规则会按新的赋值语义解释，页面必须在公式输入区明确提示这一点。

## 2. 目标用例

测试房间：`1970740553`

礼物：`心动盲盒`

当前预制目录信息：

- 礼物 ID：`32251`
- 礼物单价：`15000`

属性：`早播次数`

公式：

```text
IF(早播次数<10, 早播次数+1, 早播次数*2)
```

预期结果：

| 触发前 | 公式结果/触发后 |
|---:|---:|
| 0 | 1 |
| 9 | 10 |
| 10 | 20 |
| 20 | 40 |

## 3. 规则计算语义

现有流程中，规则引擎会把公式结果命名为 `delta`，再执行 `before + delta`。改版后必须改为：

```ts
const before = attribute.value;
const nextValue = evalFormula(rule.formula, env);
const boundedValue = applyCap(nextValue, rule.cap);
const delta = boundedValue - before;
attribute.value = boundedValue;
```

### 3.1 公式变量

- `price`：礼物单价。
- `count`：本次礼物数量。
- 目标属性名：触发前的当前值，可用于构造新值。

例如：

- `早播次数+1`：当前次数加一。
- `早播次数*2`：当前次数翻倍。
- `IF(早播次数<10,早播次数+1,早播次数*2)`：小于 10 时加一，否则翻倍。

### 3.2 限制条件

- 最低价格：仍然在公式计算前判断，不满足时不执行规则。
- 当日限次：仍然按规则触发次数限制。
- 封顶：对公式算出的目标值执行上限限制，即 `min(nextValue, cap)`。
- 负值：继续允许公式产生负值，除非已有属性/规则校验明确禁止。
- 日志：记录 `delta = boundedValue - before`，因此赋值为相同值时变化量为 0。

## 4. UI 与文案

公式编辑器需要从“增加多少”改为“触发后变成多少”：

- 输入标签：`触发后属性值` 或等价短文案。
- 预览文案：`当前值：X → 触发后：Y`。
- 说明：`公式结果会直接成为属性的新值。需要累加时，请在公式中写出当前属性名，例如：早播次数+1。`
- 公式示例更新：
  - `当前值加 60 秒` → `当前值 + price/1000*60`。
  - `每个礼物 30 秒` → `当前值 + count*30`。
  - `随机设置为 10~60` → `RANDBETWEEN(10,60)`。
  - `达到 10 次后翻倍` → `IF(早播次数<10,早播次数+1,早播次数*2)`。
- 规则列表显示公式原文，不再显示“增加”相关描述。
- 页面首次进入公式编辑器时必须能看到上述赋值语义提示，避免主播继续按旧的变化量理解公式。

## 5. 数据与兼容性

- 不改变 `GiftRule` 的 JSON 字段结构。
- 不改变 localStorage key、房间连接、礼物匹配和统计日志结构。
- 这是有意的语义破坏性变更：已有规则不做自动公式转换，导入旧配置后按赋值语义执行。
- README/配置页必须明确提醒已有规则需要复核。

## 6. 测试要求

公式引擎/规则引擎测试必须覆盖：

- 当前值 `0`、`9`、`10`、`20` 的目标用例结果。
- 直接赋值：公式 `100` 后属性为 `100`，不是 `before + 100`。
- 使用属性变量的累加：`早播次数+1`。
- 使用属性变量的翻倍：`早播次数*2`。
- 封顶作用于目标值，而不是变化量。
- 日志 delta 仍为新旧值之差。
- 最低价格、日限次和重复礼物去重行为不改变。

验收命令：

```bash

npm run build
```

## 7. 范围外

- 不增加“增加/赋值”切换控件。
- 不改变公式 tokenizer、函数集合或随机函数语义。
- 不改变 B 站连接协议、礼物目录同步和 OBS 显示页面结构。
