# Mac 开发、Hosted 主线与 Windows 兼容线设计

日期：2026-08-31

## 1. 目标

把日常开发环境迁移到 Apple Silicon Mac，同时把产品研发重心从逐步退役的 Windows EXE 转向 Hosted。Mac 和 Linux 承担日常开发、Hosted 构建、自动测试与部署验证；Windows 不再是所有改动的通用门禁，只作为 EXE 遗留兼容、迁移来源、共享核心回归、紧急修复和正式 EXE 发布的平台。

本设计不以开发环境迁移作为提前停止 EXE 支持的理由。EXE 仍是现有用户的数据来源和回退路径。只有 Hosted 完成功能覆盖、迁移、真实生产试运行和用户迁移等既定门槛后，Windows 验收强度才可以按阶段下降。

## 2. 已选择的方案

采用 **Hosted 主线 + 条件式 Windows 兼容线**：

1. Apple Silicon Mac 是主要开发环境；
2. Hosted 的 Linux、MySQL、浏览器和部署验证是全量必过门禁；
3. GitHub Actions 的 Windows x64 runner 只在改动影响 EXE、共享核心、迁移契约或 EXE 发布链时运行；
4. Windows 11 ARM 虚拟机用于 EXE 参考状态采集和偶发交互复现，不作为普通 Windows x64、显卡、驱动或硬件编码的最终证据；
5. 正式 EXE 发布继续使用现有 Windows x64 签名和产物复验流程；
6. 在进一步降低 Windows 环境投入前，冻结最后受支持 EXE 的可重复 UI 与迁移基准。

不选择以下两种极端：

- 所有 PR 都强制运行完整 Windows 流水线。这会让即将退役的产品线继续支配 Hosted 开发反馈时间；
- 立即取消全部 Windows 测试。这会破坏现有用户支持、迁移出口、共享语义和紧急安全修复能力。

## 3. 设计原则

### 3.1 产品方向决定门禁主次

Hosted 是长期目标，EXE 是迁移期产品。新增产品能力原则上进入 Hosted；EXE 只接受迁移、兼容、安全、数据保护和影响现有用户的关键缺陷修复。CI 的默认路径必须反映这一方向，而不是把两套产品长期视为同等主线。

### 3.2 按影响边界触发平台验证

是否运行 Windows 验证由改动影响的模块和契约决定，不能只根据开发者使用的操作系统决定。Hosted 专属改动不触发 Windows；共享核心和迁移契约仍必须证明未破坏 EXE；EXE 专属改动必须在 Windows x64 上构建和运行。

### 3.3 静态检查不代替目标平台运行

Mac 上的 Go 交叉编译只能发现编译错误，不能证明 DPAPI、托盘、单实例、原子替换、自动更新、Windows 进程控制、Media Foundation 或 FFmpeg 硬件路径正确。Windows ARM 上的 x64 模拟可以帮助复现用户态交互，但不能替代真实 x64 驱动和硬件环境。

### 3.4 退役由证据门槛驱动

Windows 门禁只能在对应退役阶段的进入条件满足后降低。日期、开发设备变化或 Hosted 测试变绿都不能单独触发降级。任何硬门槛失败都回到上一阶段，并继续保留对应 EXE 支持能力。

## 4. 平台与责任边界

| 平台 | 主要责任 | 不承担的责任 |
| --- | --- | --- |
| Apple Silicon Mac | 日常编码、TypeScript/Go 单元测试、前端构建、Hosted 本地开发、浏览器调试 | 最终 Windows x64 运行、签名、驱动和硬件编码验收 |
| Linux CI / Hosted 测试环境 | Hosted 构建、MySQL 集成、部署资产、服务端安全与运行时测试 | EXE 桌面交互和 Windows API 行为 |
| GitHub Windows x64 runner | 条件式 EXE 构建、Windows 专属 Go 测试、打包后冒烟、正式签名和发布复验 | 显卡、真实 OBS 插件组合和人工桌面体验 |
| Windows 11 ARM 虚拟机 | EXE UI 基准采集、迁移导出、托盘/单实例/DPAPI 等偶发交互复现 | 普通 Windows x64 性能、驱动、显卡、硬件编码最终结论 |
| 临时真实 Windows x64 环境 | 高风险 FFmpeg/Media Foundation、OBS、驱动或硬件问题的发布前验收 | 日常 Hosted 开发 |

不要求购买或长期维护专用 Windows 实机。只有出现高风险 Windows 专属改动时，才临时使用实际 x64 设备、可信云桌面或具有相同硬件能力的环境；如果无法获得该环境，验收记录必须明确标为未覆盖，不能把 ARM 模拟结果写成已通过。

## 5. CI 门禁模型

### 5.1 始终运行的 Hosted 主门禁

所有 PR 至少运行以下检查：

- `npm test`；
- `npm run typecheck`；
- `npm run build:hosted`；
- Hosted Go 测试与 `go vet`；
- Hosted 构建产物和静态资源闭包验证；
- 触及 MySQL 持久化时运行隔离的 MySQL 集成测试；
- 触及部署合同、运行时、OBS 或迁移时运行相应集成测试；
- 迁移 EXE 页面或交互时运行 Hosted 浏览器 E2E 和视觉对比。

这些检查构成分支保护的主门禁。Hosted 的生产状态仍以真实部署、备份恢复、长连接、容量、跨网络观察和试运行记录为准；CI 通过不能升级生产成熟度标记。

### 5.2 条件式 Windows 兼容门禁

新增一个逻辑上的 `windows-compat` 作业，并由仓库内可测试的路径分类脚本决定运行级别。分类结果和命中的原因写入作业摘要，避免维护者不知道 Windows 为什么运行或跳过。

| 改动范围 | Windows 级别 | 必须验证 |
| --- | --- | --- |
| Hosted 专属 Go、Hosted 前端、`deploy/hosted/` | `skip` | 记录“Hosted-only”原因，不启动 Windows runner |
| 共享玩法核心、共享契约、迁移 schema、桌面适配器 | `shared` | Windows x64 编译、受影响 Go 测试、迁移契约测试 |
| EXE UI、桌面 Go 入口、资源嵌入和构建脚本 | `desktop` | `npm run build:ui`、`npm run build:exe`、Windows Go 测试、打包资源和路由冒烟 |
| DPAPI、托盘、单实例、原子替换、更新器、FFmpeg/Media Foundation | `desktop-high-risk` | 完整 Windows x64 自动测试、产物冒烟，并按风险要求人工验收 |
| EXE 标签或手动正式发布 | `release` | 现有发布流水线全部签名、摘要、FFmpeg、更新清单和发布后复验 |

第一版路径规则必须采用显式允许列表，不得用“所有 `.go` 文件都触发 Windows”这种过宽规则，也不得只匹配文件名而漏掉共享依赖。路径分类脚本本身需要单元测试，覆盖新增、重命名、删除以及同时命中多个级别的情况；多个级别同时命中时取最高级别。

### 5.3 分支保护汇总

提供一个始终执行的 `ci-gate` 汇总任务：

1. Hosted 主门禁失败时失败；
2. `windows-compat=skip` 时记录跳过原因并成功；
3. Windows 作业被要求但未运行、取消或失败时失败；
4. 高风险改动缺少所需人工验收证据时，不允许进入 EXE 发布；
5. 汇总状态是分支保护引用的稳定检查名，避免条件任务被跳过时分支保护悬空。

Windows runner 不接收正式签名凭据。只有受保护标签或明确的手动发布流程可以进入现有 `release` Environment 并使用 EVSign 凭据。

## 6. Mac 日常开发闭环

### 6.1 本地快速反馈

Mac 环境使用仓库锁定的 Node.js、Go 和前端依赖。默认反馈链为：

```text
编辑
→ 相关单元测试
→ TypeScript 类型检查
→ Hosted 前端构建
→ Hosted Go 测试
→ 提交 PR
```

开发者可在 Mac 上增加 Windows amd64 交叉编译检查，但该检查只命名为 `compile`，不能命名或描述为 Windows 验收。当前 `scripts/build-go.mjs` 的正式职责仍是构建 Windows EXE；若后续需要 Mac 调用，必须显式设置目标平台并保持与 Windows CI 相同的资源输入。

### 6.2 Windows 缺陷修复反馈

Windows 自动化失败时：

1. 保存 commit SHA、runner 镜像、失败测试、EXE、日志和 SHA-256；
2. 优先根据自动测试在 Mac 增加跨平台回归用例；
3. 只有 Windows API 或桌面状态无法在 Mac 重现时才启动 ARM 虚拟机；
4. 修复始终回到 Mac 的同一分支完成，不直接修改虚拟机里的代码副本；
5. 推送后由同一 Windows x64 作业重新构建和验证；
6. 硬件或驱动问题在临时真实 x64 环境复验，并记录未能自动化的原因。

失败产物必须去除 Cookie、令牌、UID、昵称、消息内容和原始礼物数据。凭据类测试使用临时测试账户或替身，不上传真实用户数据。

## 7. EXE 与 Hosted UI 迁移基准

### 7.1 冻结基准的时机

在 EXE 进入功能冻结、Windows 环境进一步降级前，创建最后受支持 EXE 的可重复 UI 基准。基准绑定：

- EXE 版本和 commit SHA；
- 测试配置、固定数据和状态初始化方式；
- 浏览器/页面入口；
- 视口尺寸和缩放比例；
- 页面状态与交互步骤；
- 截图或短录屏的 SHA-256。

基准不包含真实凭据、用户身份、历史礼物、私人素材路径或可访问的 OBS 长期令牌。

### 7.2 覆盖范围

每个迁移功能至少覆盖：

- 空状态、已有数据、加载中、错误、只读或禁用状态；
- 编辑、保存成功、校验失败、取消、删除确认等相关交互；
- 弹窗、抽屉、下拉菜单、提示和焦点状态；
- 桌面宽屏、常用窄屏和移动布局；
- 页面结构、组件层级、间距、控件、状态、响应式布局和交互结果。

验收必须直接并排查看 EXE 与 Hosted 截图，必要时生成像素差异图。只对齐外壳、标题栏或部分卡片不算完成。Hosted 独有内容可以新增，但必须沿用 EXE 的设计语言、组件模式和交互语义，并保证新增内容不会破坏被迁移区域的层级和响应式行为。

### 7.3 基准的使用

冻结后，普通 Hosted UI 迁移优先与已版本化的基准对比，不要求每次重新启动 Windows。只有以下情况重新采集 EXE：

- 发现基准未覆盖的重要状态；
- EXE 因关键缺陷修复改变了应迁移的用户语义；
- 截图环境或状态夹具被证明不确定；
- 迁移范围依赖此前未固定的桌面行为。

截图和测试报告是否进入 Git，由后续实施计划按“正式验收资产”与“本地实验资产”区分。临时比较图默认不提交；最终被引用的基准、状态清单和生成规则应作为正式产品迁移合同受版本控制。

## 8. EXE 数据迁移验收

Windows 兼容线还负责证明迁移来源可靠。最低闭环为：

```text
最后受支持 EXE
→ 导出白名单迁移包
→ Hosted 上传和严格校验
→ 预览迁移/忽略/不兼容项
→ 用户确认
→ 运行中屏障或离线应用
→ Hosted 状态和 UI 验证
→ 七天内回滚验证
```

EXE 导出和 Hosted 导入使用独立版本的迁移协议，不建立双向同步。每个受支持玩法单元都必须有固定夹具，验证配置、当前玩法状态和依赖完整迁移。凭据、观众身份、送礼历史、日志、媒体文件、素材 URL、桌面更新设置和 localhost OBS 地址不得进入迁移包。

EXE 不能退役到下一阶段，除非所有声明支持的迁移内容都已完成导出、预览、应用、故障恢复和回滚证据。发现不能迁移的桌面能力时，必须先提供 Hosted 等价能力或明确批准的替代方案，不能静默丢失。

## 9. 生命周期与 Windows 投入降级

### 9.1 阶段 A：迁移开发期

状态：Hosted 正在补齐核心与媒体能力，EXE 继续支持现有用户。

- Hosted 主门禁对所有 PR 必过；
- Windows 按路径运行 `shared`、`desktop` 或 `desktop-high-risk`；
- ARM 虚拟机保留干净快照；
- EXE 正式发布保持完整签名和复验；
- 开始建立 EXE UI 与迁移基准。

退出条件：生产基础、核心功能、媒体功能和迁移出口达到已批准的覆盖要求，且基准资产完整。

### 9.2 阶段 B：封闭试用与自愿迁移期

状态：Hosted 已覆盖目标功能，进入真实用户和真实网络验证。

- EXE 不再增加新产品能力；
- Windows 只覆盖共享核心、迁移出口、更新安全和关键缺陷；
- UI 基准通常不重新采集；
- Hosted 必须完成香港真实部署、备份恢复、容量、共享房间、真实 B站长连接、跨网络和连续观察；
- 用户自愿迁移，保留既定回滚窗口。

退出条件：试运行证据、迁移成功率、回滚、用户通知和支持策略全部达标。

### 9.3 阶段 C：EXE 功能冻结

状态：Hosted 成为默认产品，EXE 只保留迁移和紧急支持。

- 条件式 Windows PR 作业只对迁移、安全和紧急修复运行；
- 完整 Windows 套件改为定期或手动运行，用于发现工具链腐化；
- 保留最后可复现构建输入、签名配置说明、更新链和迁移工具；
- 公开停止维护日期前再次验证下载、安装、迁移和 Hosted 回退路径。

退出条件：公告窗口结束，现有用户有可验证的迁移或明确的离线处置方案。

### 9.4 阶段 D：停止维护

状态：不再进行日常 EXE 产品维护。

- 移除普通 PR 的 Windows 必过要求；
- 归档最后签名 EXE、摘要、发布元数据、源版本、构建说明和迁移说明；
- 保留 Hosted 对历史迁移包版本的明确支持或拒绝策略；
- Windows ARM 虚拟机可以删除，但应先验证所有正式基准和迁移夹具可在非 Windows 环境读取与复验；
- 后续是否提供安全紧急修复必须由单独支持政策决定，不能暗示永久支持。

任何阶段发现硬门槛缺失，都回到上一阶段；不能通过修改阶段名称绕过证据要求。

## 10. 可观察性与验收证据

每次自动或人工验收至少记录：

- commit SHA、分支或标签；
- CI runner 操作系统、架构和镜像版本；
- Node、Go、浏览器和关键外部工具版本；
- 构建产物名称、大小和 SHA-256；
- 实际执行与跳过的门禁及原因；
- 自动测试报告；
- 人工验收使用 ARM 模拟、云端 x64 还是真实 x64；
- EXE/Hosted 截图对应的页面、状态和视口；
- 未覆盖项、失败处置和是否阻塞迁移或发布。

Hosted 生产验收证据继续写入专用 pilot checklist 或部署记录，不混入普通 CI 日志。CI 只能证明代码和构建层，不能证明生产网络、真实 B站连接、备份恢复或连续运行已经完成。

## 11. 失败处理

- Hosted 主门禁失败：阻止合并，与 Windows 是否跳过无关；
- 路径分类不确定：安全地提升到更高 Windows 级别并在作业摘要说明；
- Windows runner 暂时不可用：受影响 PR 保持未通过，不用 Mac 交叉编译代替；
- ARM 虚拟机与 x64 CI 结果冲突：以目标用户的真实 x64 环境为最终判定，并保留两边证据；
- 截图差异由非确定数据导致：先修复状态夹具和采集环境，再判断 UI；
- Hosted 缺少 EXE 完整功能或交互：迁移功能不算完成，返回实现阶段；
- 正式 EXE 签名、摘要或更新复验失败：停止发布，不允许用未签名开发产物替换；
- 退役门槛失败：恢复上一阶段的 Windows 支持和验收强度。

## 12. 安全边界

- PR Windows 作业不加载 EVSign、COS、Hosted 生产或 B站真实凭据；
- 正式签名只在受保护的发布 Environment 中进行；
- CI 产物和日志不得保存 Cookie、会话、OBS 长期令牌、私钥或原始礼物数据；
- Windows 虚拟机快照不得包含发布凭据，避免把个人开发设备变成签名信任根；
- Hosted 和 EXE 发布基础设施继续保持域名、主机、凭据和业务路由隔离；
- 最后签名 EXE 和迁移工具归档时同时保存摘要、签名发布者和来源 commit，不能只保存一个裸 EXE。

## 13. 非目标

- 不为 Hosted 新功能维护一套新的 EXE 实现；
- 不把 Windows ARM 作为新的正式发布架构；
- 不在本设计中增加 Windows ARM64 EXE；
- 不购买或部署长期 Windows 自托管 runner；
- 不改变现有 EXE 签名服务商、发布者或 COS 镜像架构；
- 不提前宣布 EXE 停止维护日期；
- 不在本设计中实现 Hosted 尚缺失的业务功能；
- 不把临时截图、实验脚本和诊断报告默认提交到 Git。

## 14. 实施边界与验收标准

后续实施计划应拆成可独立验证的任务，至少覆盖：

1. Hosted 主 CI 及稳定的 `ci-gate`；
2. 可测试的路径分类器和条件式 `windows-compat`；
3. Windows x64 开发版 EXE 构建、启动、路由和退出冒烟；
4. Mac 开发命令和“交叉编译不等于验收”的维护文档；
5. Windows ARM 虚拟机基准采集清单；
6. EXE/Hosted UI 状态与视口矩阵；
7. 迁移导出、预览、应用和回滚夹具；
8. 生命周期阶段、切换证据和回退规则；
9. 现有正式 `release.yml` 的隔离和不回归验证。
